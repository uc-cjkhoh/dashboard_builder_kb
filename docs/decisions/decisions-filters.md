# Decisions — filters

Part of the [decisions](decisions-platform.md) record: one decision, edited in place when it changes.

### D82 — A calculated field is a row filter, applied before grouping
Decided 2026-11-02 (autonomous build). A calculated field may be a **Filters** field; a calculation that aggregates may not.
- **Order of operations:** the calculation's compiled row-level expression is one more `WHERE` condition, `AND`ed with the plain filters, the selection, the drill path, the page and the date range. Rows are filtered **before** any aggregate runs, **before** a Top-N ranks its members (a Top-N ranks within the rows the other filters keep, as it already does for plain filters), and before table calculations and the display cap, which work on the grouped result. The Evaluation order popover counts it as a row-level calculation.
- **An aggregate calculation is refused** (400 at `filters[i].calc`, and a toast on drop): an aggregate has no row to test. Cutting groups after aggregation is a different control, a filter on a measure of the view ([D84](#d84--a-filter-on-an-aggregated-measure-having-keeps-groups-after-grouping)); an aggregate calculation as a *row* filter waits for the level-of-detail work ([backlog](../development/backlog/calculations.md)).
- **Wire:** `QueryFilter.calc` carries the tree; `db` and `table` are empty and `column` is the calculation's label (≤ 60 characters, as for a dimension). The compared values are bound as `p{i}`, the calculation's own literals as `c{n}`; the calculation goes through the one calc compiler, so identifiers are catalog-checked and quoted in `Identifier.cs` and a field on a table not in the query is a 400 (the worksheet adds the calculation's tables to the joins). Values are coerced by the calculation's **type** (number, text, date, boolean), with the same rules as a plain column; a calculation takes no cast.
- **Operators:** all of a plain field's except `top` (400 `filters[i].calc`) and, for a date, `in the` (a calculation's date width is unknown). `=` / `!=` / ordering on a calculation that yields NULL drop those rows, while `not in` keeps them (as for a plain column). No new limits: the 20-filter, 500-value and 1000-character bounds apply unchanged and are already mirrored in `Core/validate.js`.
- **Not shared:** a shared filter applies where its table is in the view; a calculation has no one table, so **Apply on every dashboard** is not offered.
- **Rejected:** evaluating the filter in the browser (the result is bounded, the filter must cut rows first); `HAVING` through the row-filter path; sending the calculation's name instead of its tree (the server holds no calculations).

### D84 — A filter on an aggregated measure (`HAVING`) keeps groups after grouping
Decided 2026-11-06 (autonomous build). A measure pill may carry a number condition on its aggregated value; the server keeps only the groups that pass. Smallest slice: a number compared with one of the view's own measures.
- **Order of operations:** `WHERE` (row filters, selection, drill, page, date range) → **Top-N** ranking → `GROUP BY` → **`HAVING`** → `ORDER BY` → `LIMIT` (the 5000-group cap, or the page). The cap and the truncation probe therefore count only groups that pass, and the table's total (`withTotal`) counts the same groups.
- **Top-N and the measure filter:** the Top-N ranks its members under the row filters only (as before, D82), and the measure filter then cuts those groups, so *Top 10 customers by sum, where sum is above 1000* can show fewer than 10. It never re-ranks. Rejected: ranking after `HAVING` (Top-N would change meaning depending on another control, and its subquery would need the measure filter too).
- **The Other bucket is not combined with it.** "Other" is the total of the groups past the cap; with a measure filter it would have to total only passing groups, so a request with both is a **400** at `otherBucket`, and the browser leaves the bucket out when a measure filter applies. Rejected: a silent drop on the server (a request that quietly means less).
- **Wire:** `QueryRequest.having` = `[{ measure, op, value | values }]`. `measure` is the **index into `measures`** (0 is the implicit count when there are none), not an identifier: the clause compares the already-built `v{n}` alias, so the aggregate (plain, sampled, approximate, calculated) is written once in `AggregateSql` and no identifier or aggregate name is taken from the client. `op` is one of `= != > >= < <= between` (400 at `having[i].op`); numbers are plain finite numbers bound as `Float64` (`h{i}`, or `h{i}a` / `h{i}b` for a range, From ≤ To) — anything else is 400 at `having[i].value` / `.values`; an index outside the view is 400 at `having[i].measure`. At most **10** (`ApiLimits.MaxHaving`, `LIMITS.having`), `AND`ed. A `NULL` aggregate (a standard deviation of one value) fails every comparison and drops its group.
- **Browser:** stored on the measure pill as `having` (`{ op, value }` or `{ op: "between", values }`), edited in the pill's popup ("Keep groups where *sum amount* is at least 1000"). The pill shows the filter as a badge with an icon, and the line under the view says it in words with the grain: "Showing only groups where sum amount is at least 1000, per region." An unusable number is kept as typed, marked, **not applied** (the badge and the line say so). A filter on a size / colour / label measure or on a histogram or box plot is not sent (the line says so for the stat charts). It saves and restores with the workbook; an invalid saved one is dropped and reported.
- **Table calculations and NULLs:** the filter cuts the raw aggregate before table calculations run, so a running total or percent of total is computed over the groups that remain. A NULL aggregate (a standard deviation of fewer than two rows, ATTR) fails every comparison, `!=` included, and its group is dropped.
- **Not built:** a measure filter on a dashboard-shared control, a filter on a measure not on the view, and `HAVING` on a Top-N ranking measure ([backlog](../development/backlog/charts-and-formatting.md)).

### D87 — The measure-filter range slider reads its span from the drawn result
Decided 2026-11-06 (autonomous build). The `between` measure filter (D84) gets two range sliders in the pill popup. Smallest slice: no new request, no server change.
- **Span:** the min and max of that measure over the rows of the last drawn result, widened by the stored filter and by the widest span already seen for that same measure (sheet, field and aggregation as named, and the grouping dimensions; kept in memory, dropped on Clear). Changing the aggregation or the grain is a different key, so a stale span never carries over. A filtered result is narrower than the data, so without the memory a track would shrink with each narrowing. Rejected: a dedicated min/max query (a new endpoint and a new limit for a convenience); using only the filtered result.
- **Step:** 1 for whole-number ends spanning at least 10, else the power of ten at or below 1/100 of the span; typed values stay free-form and may sit between steps or outside the span (the slider then shows the whole span).
- **Behaviour:** dragging fills the From / To boxes, release applies (after a 0.5 s pause, so a run of arrow keys is one query) through the same write path as typing, so validation and the wire shape (`having`, D84) are unchanged. Two sliders rather than one dual-thumb widget: native, keyboard and screen-reader operable, framework-free.
- **Not built:** a slider for the one-sided operators; a span that includes groups the filter has already removed on first open (it is learned from the result drawn when the popup opens).
